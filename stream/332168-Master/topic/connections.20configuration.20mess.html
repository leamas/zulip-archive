TwoCan (Nov 26 2026 at 10:37):

Is there a need for an enable/disable option to avoid the risk of data colliding with other onboard systems?

Not really.

Transmitting PGN's 129283, 129284 and 129285 enables two things.

  1. It allows instruments displays and MFD's to display the current route and waypoint information (bearing and range to waypoint, cross track error, time to go), no different to the little widget displayed in OpenCPN when a waypoint or route is activated.
  2. When a NMEA 2000 autopilot is in Nav mode, it supplies the necessary data for the autopilot to adjust the course.
    The presence of these PGN's generated by OpenCPN does not cause the autopilot to switch from standby to nav mode, this is performed by manufacturer proprietary PGN's. It does not cause a MFD to activate a route and begin generating its own PGN's.

The only risk is if a sailor manually activates a route on both OpenCPN and a MFD. Both will generate these PGN's and two sets of conflicting PGN's may "confuse" an autopilot, or cause instrument displays to display different values. Or if the user activates a route on two different instances of OpenCPN. We cannot defend against stupidity.

As NMEA 2000 is bi-directional, removing the In/Out checkboxes should be a no brainer. One could make the case, that if PGN filtering was available for NMEA 2000, you don't even need a checkbox for "Send Navigation Data", you would just need to configure PGN's 129283, 129284 & 129285 to be accepted in the outbound filter.

An interesting thought, is to enable plugins to alter the filter. For example, the WMM plugin needs to transmit PGN 127258, the plugin should be able to add that to the list, rather than relying on the user to add the entry.

But this maybe unnecessary as in the normal use case the filter list could be empty (transmit everything) because only data that is written to CommDriverN2K gets transmitted.

I can't see any reason why the same design cannot be used for NMEA 0183. As I said, OpenCPN neither knows, nor cares whether the physical NMEA 0183 Tx connection is electrically connected to something.

Again, it doesn't need a specific checkbox to "send navigation data to an autopilot", a user just needs to enable APB, RMB and XTE sentences, whether they are prefixed with the "EC" talker Id, is unimportant. Here the filter list is important because there are two interfaces/API's, PushNMEABuffer and WriteCommDriver which behave slightly differently.

This is an opportunity to simplify the UI and make it consistent.

TwoCan (Nov 27 2026 at 14:38):

Overall yes, but a couple of nuanced points.

Should all n2k connections be similar w r t enable/input output and sending AP data?

Without delving into the code, it may be possible for OpenCPN and auto-detect to inadvertently use an Actisense protocol that may not be supported for both Receive and Transmit with a specific gateway.

For example on the Actisense W2K-2, WGX-1 and W2K-1, both ASCII Raw and Actisense Raw are not supported for Receive or Transmit on either TCP or UDP. However on the NGX-1 (USB), both N2K ASCII and ASCII Raw are Receive only.

What this really means is that depending on the gateway, some protocols cannot be considered to be bi-directional. We don't have the ability for the user to configure a protocol, we currently rely on auto-detect.

  1. Should n2k connections have a "Send AP/Repeater info" checkbox? Tentative answer: yes.

Assuming core OpenCPN always generates PGN's 129283, 129284 and 129285 when a waypoint or route is active and that this checkbox merely filters these PGN's from the connection, then in the absence of a NMEA 2000 filter, this is the only solution.

Later if an output filter capability was added, then this checkbox could be omitted and the guidance to the user to would be to configure a filter to accept or refuse the navigation PGN's, in a similar way that setting a filter for APB, RMB and XTE sentences for NMEA 0183 connections is done today.

TLDR: Yes, in agreement.
