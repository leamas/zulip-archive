Alec Leamas (Nov 25 2026 at 17:39):

@Håkan Svensson @Douwe Fokkema @TwoCan @Dave Register @Pavel Kalian

We have some inconsistencies when configuring n2k interfaces

  • N2k over TCP/UDP and regular serial connections does have checkboxes enabling input and/or output; N2k over socketcan and slcan does not have such checkboxes
  • The "is driver output capable" is used to govern whether the autopilot pgns should be sent. socketcan/slcan are hardcoded as in/out and have no possibility to disable this.
  • For N0183, all connections have the enable input/output checkboxes, the output checkbox overloaded with sending autopilot info
  • Plugins scans the available drivers for those are marked as being capable of output and uses this/these sending data.

Together, a considerable mess. @TwoCan and I have discussed this, and for n2k we think that:

  1. All n2k connections are bidirectional, being capable of both input and output. There is thus no need for "enable input/output " checkboxes for n2k connections.
  2. OTOH, a checkbox for "send autopilot info" is required.

For n0183, things are perhaps more complicated. First question becomes if we actually have n0183 connections which are physically output or input only. Such wiring is certainly possible, but is it actually used?

That is, would it be OK to simplify 0183 connections like for n2k above? Hardcoded input + output, a separate "Send autopilot info" checkbox?

Thoughts?

Håkan Svensson (Nov 25 2026 at 18:19):

A N0183 connection is not like a N2k bus, i.e. a single data wire. We have one RX and one TX and they can be used to connect one or more devices. It's for example rather common to get RX from a GNSS receiver and the TX for the same RS232/USB-connection wired to a AP. Not less it's a way to save serial-USB converters. So the answer to "Such wiring is certainly possible, but is it actually used?" is "Yes".
